# skill-autoresearch: 自律リサーチループ

トピックを受け取り、Web 検索・ソース取得・合成・wiki 登録を自律的に実行するスキル。ユーザーはチャット返答ではなく wiki ページを受け取る。

トリガー例: 「[トピック] をリサーチして」「[トピック] を調べて wiki にまとめて」「[トピック] について深く調べて」「[トピック] の wiki を作って」

---

## Transport

Kiro 環境では **filesystem 固定**。Write ツールのみ使用する。obsidian-cli / MCP transport は使用しない。

---

## モード連携

ファイリング前に `python3 scripts/wiki-mode.py route research "<topic>"` を呼び出してパスを決定する:

| モード | パス |
|--------|------|
| generic | `wiki/concepts/<Topic>.md` |
| LYT | `wiki/notes/<topic>.md`（+ `wiki/mocs/<topic>-moc.md` を作成または更新） |
| PARA | `wiki/resources/<topic>/<topic>.md` |
| Zettelkasten | `wiki/<ID>-<topic>.md` |

`.vault-meta/mode.json` が存在しない場合、ルーターは generic パスを返す。

合成ページだけでなく、ループが作成するすべての新規ファイル（entity / concept / source）についても、それぞれ適切な `route` コマンド（`route entity` / `route concept`）でパスを決定すること。

---

## Web egress セキュリティガイドライン

autoresearch は WebFetch / WebSearch を使って任意の URL を取得する。各フェッチ前・vault への書き込み前に以下のガードを適用すること。

### URL 検証ルール

以下のスキームおよびターゲットは拒否する:
- `file://`・`javascript:`・`data:` スキーム — `http(s)://` のみ許可
- RFC1918 プライベートアドレス（`10.x.x.x`・`172.16-31.x.x`・`192.168.x.x`）および `localhost`/`127.0.0.1` — ユーザーの内部ネットワークへのアクセスを防ぐため
- 直前の WebSearch ステップで表示されなかったホスト（保守的に判断すること。検索結果に現れなかったドメインへのリダイレクトは追わない）

### コンテンツサニタイズルール

取得した HTML を wiki ページに書き込む前に必ず実施:
- `<script>`・`<iframe>`・`<style>` タグとその内容を除去する
- ソース本文の `[[` と `]]` をエスケープする（`\[\[` または HTML エンティティ `&#91;&#91;`）— 悪意あるコンテンツが vault のリンクグラフに wikilink を挿入できないようにするため
- 取得コンテンツ内の `---` YAML frontmatter 区切り文字を拒否する — source ページの frontmatter はループが作成し、取得元ソースは関与しない
- 取得本文を約50KB に切り詰めてコンテキスト肥大化を防ぐ

### コスト通知

フル実行は最大 **3ラウンド × 5ソース × 3アングル ≈ 45回の WebFetch** になる。WebFetch は Anthropic プランでメータリングされる。`program.md` の `max_pages: 15` はファイリングコストを制限するが、フェッチ数は制限しない。コストの高いトピックのリサーチを開始する前に、このコスト見積もりをユーザーに伝えること。

### 失敗時の処理

フェッチが失敗した場合（タイムアウト・4xx/5xx・コンテンツ過大・サニタイズにより内容がなくなった場合）は、URL と理由を `wiki/log.md` に記録してループを継続する。実行全体を中断しない。また無音でスキップしない — スキップされたソースはすべて、合成ページの「未解決の問い」セクションに記載すべき情報である。

## Concurrency（並列書き込み安全性）

autoresearch は1トピックあたり10〜30ページの書き込みが発生する高頻度書き込みスキル。すべての wiki ページ書き込みは必ず `wiki-lock acquire` を先行させること:

```bash
bash scripts/wiki-lock.sh acquire wiki/sources/<slug>.md || sleep 2 && bash scripts/wiki-lock.sh acquire wiki/sources/<slug>.md
# Write ツールで書き込む
bash scripts/wiki-lock.sh release wiki/sources/<slug>.md
```

autoresearch が並列実行された場合（同じトピックや重複するトピックで複数の実行が同時に走った場合）、ロックにより同一の source / concept / entity ページが同時に書き込まれないようにする。取得に失敗した側はそのパスをスキップして `wiki/log.md` に記録し、次のイテレーションで取得できるようにする。

## リサーチ開始前の準備

**`wiki/references/program.md` を必ず読み込む。** このファイルにはリサーチ目標・信頼度スコアリング基準・ループ制約・ドメイン固有の指示が含まれており、ユーザーが編集できる。リサーチ前に毎回読み込んで内容を把握すること。

## トピック選択

### A. 明示的な指定（常に優先）

ユーザーが「[トピック] をリサーチして」や「[トピック] について調べて」と言った場合、そのトピックをそのまま使用して以下のセクションをスキップする。

### C. ユーザーに確認（明示的な指定がない場合）

トピックが明示されていない場合は「どのトピックをリサーチしますか？」と質問する。

> **注**: DragonScale boundary-first 選択（セクション B）は P2 機能のため除外。

## 研究ループ

```
入力: トピック（上記「トピック選択」より）

ラウンド 1. 広範検索
1. トピックを3〜5の異なる検索アングルに分解する
2. 各アングルに対して2〜3つの WebSearch クエリを実行する
3. アングルあたり上位2〜3件の結果に WebFetch を実行する
4. 各ページから「主要な主張・エンティティ・コンセプト・未解決の問い」を抽出する

ラウンド 2. ギャップ補完
5. ラウンド1から不足している点・矛盾している点を特定する
6. 各ギャップに対してターゲット検索を実行する（最大5クエリ）
7. 各ギャップの上位結果に WebFetch を実行する

ラウンド 3. 合成確認（ギャップが残る場合のみ実施）
8. 重大な矛盾や欠落が残っている場合: もう1回ターゲット検索を実施する
9. そうでなければ: ファイリングに進む

最大ラウンド数: 3（program.md で設定）。深度に達するか最大ラウンド数に達したら停止する。
```

## ファイリング規則

リサーチ完了後、以下のページを作成する:

**wiki/sources/**（モードに応じてルーターが決定）: 見つかった主要な参考文献ごとに1ページ
- frontmatter: `type: source`, `source_type`, `author`, `date_published`, `url`, `confidence`, `key_claims`
- 本文: ソースの要約と、そのトピックへの貢献内容

**wiki/concepts/**（モードに応じてルーターが決定）: 抽出した重要なコンセプトごとに1ページ
- 単独で成立するほど実質的なコンセプトの場合のみ作成する
- 先にインデックスを確認すること: 重複作成を避け、既存のコンセプトページを更新する

**wiki/entities/**（モードに応じてルーターが決定）: 特定した重要な人物・組織・製品ごとに1ページ
- 先にインデックスを確認すること: 既存の entity ページを更新する

**wiki/questions/**（モードに応じてルーターが決定）: 「Research: [トピック]」というタイトルの合成ページを1枚
- これはマスター合成ページ。すべての情報がここに集約される
- セクション: 概要・主要な発見・エンティティ・コンセプト・矛盾・未解決の問い・ソース
- このセッションで作成したすべてのページへの related リンクを含む frontmatter

## 合成ページの構造テンプレート

```markdown
---
type: synthesis
title: "Research: [トピック]"
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags:
  - research
  - [topic-tag]
status: developing
related:
  - "[[このセッションで作成したすべてのページ]]"
sources:
  - "[[wiki/sources/ソース1]]"
  - "[[wiki/sources/ソース2]]"
---

# Research: [トピック]

## 概要
[発見内容を2〜3文で要約]

## 主要な発見
- 発見1（出典: [[ソースページ]]）
- 発見2（出典: [[ソースページ]]）
- ...

## 主要エンティティ
- [[エンティティ名]]: 役割・重要性

## 主要コンセプト
- [[コンセプト名]]: 1行の定義

## 矛盾点
- [[ソースA]] は X と述べている。[[ソースB]] は Y と述べている。[どちらがより信頼できるかとその理由の簡潔なメモ]

## 未解決の問い
- [リサーチで完全には答えられなかった問い]
- [より多くのソースが必要なギャップ]

## ソース
- [[ソース1]]: 著者・日付
- [[ソース2]]: 著者・日付
```

## ファイリング後の処理

1. `wiki/index.md` を更新する。新規ページをすべて適切なセクションに追加する
2. `wiki/log.md` の**先頭に**追記する:
   ```
   ## [YYYY-MM-DD] autoresearch | [トピック]
   - ラウンド数: N
   - 取得ソース数: N
   - 作成ページ: [[ページ1]], [[ページ2]], ...
   - 合成ページ: [[Research: トピック]]
   - 主要な発見: [1文]
   ```
3. `wiki/hot.md` をリサーチサマリーで更新する

---

## ユーザーへの完了レポート

すべてのファイリングが完了したら、以下の形式で報告する:

```
リサーチ完了: [トピック]

ラウンド数: N | 検索数: N | 作成ページ数: N

作成ファイル:
  wiki/questions/Research: [トピック].md（合成ページ）
  wiki/sources/[ソース1].md
  wiki/concepts/[コンセプト1].md
  wiki/entities/[エンティティ1].md

主要な発見:
- [発見1]
- [発見2]
- [発見3]

未解決の問い（ファイリング済み）: N件
```

## 制約事項

`wiki/references/program.md` の制約に従う:
- 最大ラウンド数（デフォルト: 3）
- セッションあたりの最大ページ数（デフォルト: 15）
- 信頼度スコアリングルール
- ソース優先ルール

制約と完全性が競合する場合は制約を優先し、省略した内容を「未解決の問い」セクションに記録する。
